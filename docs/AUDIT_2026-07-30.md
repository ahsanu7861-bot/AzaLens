### 11. The Shariah gate on every surface — **Verified, with two caveats**
- Enforcement is server-side at the single exit point: `masterAnalysisService.js:1991–1998` applies `applyComplianceGate`, which replaces `trend`, `agreement`, `explanation` with withheld stubs whenever compliance ≠ CONFIRMED-and-fresh (`complianceGateService.js:96–118`). The verdict fields never leave the backend.
- `/api/explanation/:symbol` routes through `getMasterAnalysis` (`explanationService.js:20–23`), so it returns only the gated explanation. Verified.
- The legacy ungated `/trend` and `/agreement` routes were removed (`server.js:604–610` documents this).
- Scanner, search, watchlist, portfolio CRUD carry no verdicts at all.
- The frontend adds default-deny on top (`AnalysisPage.tsx:95–96`: verdict renders only when `complianceGate.unlocked === true`).
- Missing values are printed as `Unavailable`/`Review required`, never estimated: every provider field goes through `toNullable*` → `null` (`halalTerminalProvider.js`), and `IslamicCompliance.tsx:116–164` renders `"Unavailable"` for each null ratio. No estimation path exists.

**Caveat A:** `/api/portfolio/intelligence` (`portfolioIntelligenceService.js:74–98`) reads `analysis?.trend?.trend ?? "Unknown"` from the gated response. When withheld, the stub has no `.trend`, so it emits the string `"Unknown"` — **no verdict leaks**, but the surface silently converts "withheld for Shariah reasons" into a bland "Unknown" instead of an honest withheld state. No frontend page calls this endpoint today.
**Caveat B:** the raw indicator routes (`/rsi/:symbol`, `/macd/:symbol`, etc.) are public and ungated. They expose observations, not verdicts, which is consistent with "market data and evidence remain available" — but they are also unauthenticated provider-quota spenders (see Part 2, finding N1).

### 13. Finnhub missing `.catch` — **Confirmed. Real crash path.**
`finnhubProvider.js:581–586`: `pendingQuoteRequests.set(normalizedSymbol, requestPromise.then(({ result }) => result))` stores a **derived** promise with no rejection handler. Precise crash path: a quote request misses cache → `requestPromise` rejects (Finnhub timeout, 429, network error) → the awaiting caller's rejection *is* caught (`:605–623`) and returns a graceful failure — but the derived `.then(...)` promise stored in the map **also rejects**, and if no second concurrent caller happened to `await` it, that rejection is unhandled. On Node's default settings an unhandled rejection **terminates the process**. On Render free tier that means a visible outage until spin-up. This should be the first code fix approved.

## Part 2 — New findings not in the briefing

**N1 — Anyone on the internet can spend the Shariah token budget.** The API is unauthenticated. `/api/analyze/:symbol` triggers live screening (5 tokens per uncached symbol). At 10 req/min a stranger (or a search-engine crawler hitting shared analysis URLs) could drain the remaining ~177 tokens in under an hour. The budget guard caps spend at the *configured monthly budget*, not at zero — it protects against runaway bugs, not strangers. Acceptable while nobody knows the API exists; must be closed (auth, or an app-token header) before any public link circulates. *(Rules 17, 23.)*

**N2 — `/api/portfolio/intelligence` is live, expensive, and unused.** No frontend page calls it, yet each call runs a full master analysis — including live Shariah screening — for **every** holding. Combined with N1, it is the cheapest way for an outsider to spend tokens (one request, many holdings). Recommend unmounting it until a page actually needs it.

**N3 — Cold-start embarrassment risk.** Render Free spins down after ~15 idle minutes; the first request then takes tens of seconds. In a live demo before the Mufti or the lawyer, the first analysis will appear broken. Warm the backend minutes before any meeting.

**N4 — No legal surface exists at all.** No footer, no Terms, no Privacy Policy, no site-wide disclaimer. Honest disclaimers exist *inside* analysis workspaces (`ThesisWorkspace.tsx:81`, `RiskAssessment.tsx:309`, `IslamicCompliance.tsx:267–271`, scanner disclaimer) but a visitor's first screen — the landing page — carries none. *(Rules 20, 24, 26.)*

**N5 — Landing page is a different product visually.** Dark-only, Tailwind-default emerald/slate, no shared tokens, no reduced-motion consideration, while the app is a cyan/night-day token system. Detailed in `docs/DESIGN_SYSTEM.md`.

**N6 — Provider names are exposed in API responses** (`provider: "Finnhub"`, `"Halal Terminal"`, provenance fields). Rule 12 says hide providers unless attribution is required. Whether Halal Terminal's terms *require* attribution is unknown — needs a licensing check before deciding to hide or keep.

**N7 — Watchlist has no server-side size cap.** Scan selection caps at 20, but the watchlist itself can grow unbounded via POST. Minor today; matters when combined with N2.

## Part 3 — Are we ready for specialist review?

### A. Shariah readiness (for Mufti Ejaz Ahmed Samadani sahib)

**A1. Does AzaLens compute any religious ruling?** No. The boundary is clean and locatable: `halalTerminalProvider.fetchScreening` fetches the external AAOIFI screening; `shariahComplianceService.transformProviderResult` reshapes it without inference — every ambiguous field becomes `null`/`UNKNOWN`, never a guess. The status shown to users is exactly the provider's status. **One nuance to disclose to the Mufti:** `analysisTrustService.buildFundamentalInvalidation` (`:445–490`) re-checks two numeric boundaries locally (debt/assets > 30%, impermissible income > 5%) as *thesis-invalidation triggers*. This is presented as a research boundary, not a ruling — but it is AzaLens applying AAOIFI-style thresholds to provider numbers, and a scholar should hear that from us, not discover it.

**A2. Does the gate genuinely withhold on every surface?** *(The most important question.)* **Yes, with the caveats in item 11.** Withholding happens once, server-side, at the only exit point that carries a verdict. Explanation endpoint: gated. Scanner/search/watchlist/portfolio pages: carry no verdict. Legacy verdict routes: removed. Frontend: default-deny second layer. The only blemishes are the unused `/api/portfolio/intelligence` degrading "withheld" to the label `"Unknown"` (no leak, but not honest labelling), and public raw-indicator routes exposing observations (consistent with the stated policy that evidence remains available). **No surface was found where an unconfirmed stock leaks a directional verdict.**

**A3. Does it ever estimate a missing screen?** No estimation path exists anywhere. Missing values render as "Unavailable"; unknown status renders as "Review required".

**A4. Is purification presented adequately?** **This is the weakest Shariah surface.** Purification is one metric row: "Dividend purification — {rate | Unavailable}" with a one-line caption (`IslamicCompliance.tsx:154–164`). There is no explanation of the obligation, no computation against the user's actual holdings and dividends, and no methodology note. A scholar will likely judge this insufficient *as presentation* even though it is honest. Fix before the meeting: a short "Purification" explainer section in the Shariah workspace.

**A5. Does anything imply religious authority or endorsement?** No. The disclaimer "This automated screen is for research and is not a fatwa, religious ruling, or personal investment advice" is on the Shariah panel, and the backend injects an equivalent fallback disclaimer. No certification claims, no scholar names, no board implied. `scholar_attestations` is passed through from the provider verbatim if present — worth checking with the provider what it can contain before a scholar sees it.

**A6. Is the methodology documented where a scholar could inspect it?** **No.** There is no user-facing methodology page: no statement of which AAOIFI standard/version, screening date semantics, the 30%/5% thresholds, cache staleness rules (24h cache, 7-day stale boundary in `analysisTrustService.js:6`), or limitations. Version strings exist in code (`AAOIFI_METHODOLOGY_VERSION = "0.5.0"`) but nothing a Mufti can read. **This is a required pre-review fix.**

### B. Regulatory readiness (for Tahir Khan sahib)

**B7. Execution capability?** None, verified: no broker connection, no order placement, no custody, no live payment flow anywhere in backend or frontend. The Pro dialog has no payment mechanism behind it — which is itself the problem, see B8.

**B8. Advice-crossing language?** The application itself is careful: "analytical bias, not guaranteed financial outcome", "not a guaranteed outcome or personalized instruction", "Indicator agreement—not a guarantee of future performance". **The landing page is the violation:** a product mockup displaying "Verdict: BUY", "AI confidence 92%", and a trade plan with entry/targets, unlabelled as illustrative. A regulator-minded reader will screenshot exactly that. Additionally, "AzaLens Pro … Upgrade to unlock" implies a commercial offering that does not exist — awkward under Rule 26 (payments before the regulatory memo must not go live, and here the UI *implies* they already can).

**B9. Disclaimers present and visible?** Present inside analysis surfaces; **absent on the landing page and dashboard; no Terms or Privacy Policy exist at all.** Not buried — missing.

**B10. False licence/registration claims?** None found. No jurisdiction, licence, or regulated status is claimed anywhere.

### C. Product readiness

**C11. First-time walk-through.** Landing (visually divergent, BUY mockup, no footer) → search or `/dashboard` (honest, clean) → analysis page (genuinely strong: evidence, provenance, gate, withheld states) → scanner/watchlist/portfolio/settings (honest, functional, plainly labelled limitations). What breaks confidence: the cold-start delay (N3); most tickers showing "Review required" because screening is unscreened/uncached (correct behaviour, but a reviewer should be shown a pre-screened ticker so they see the full experience); the PRO badge; the landing/app inconsistency.

**C12. Visibly incomplete or contradictory.** The PRO export button (feature doesn't exist); empty `features/auth`; landing preview contradicting the real verdict philosophy; `design/*.ts` contradicting the shipped design; stale roadmap/status docs contradicting the code in both directions.

**C13. The three most credibility-damaging things, and cost to fix:**
1. **The landing page "BUY / 92%" mockup + missing disclaimers/footer** — contradicts the product's entire ethic in the first 10 seconds, in front of both specialists. Fix: replace the preview with the real differentiator (a withheld verdict + AAOIFI panel), add a footer with honest disclaimers. Small frontend change, zero provider cost.
2. **The "AzaLens Pro — Upgrade" upsell** — claims a paid tier that is Not Built; worst possible thing for the lawyer to click. Fix: remove or relabel as "Planned". Trivial change.
3. **No methodology/purification documentation for the Mufti (A4 + A6)** — he is being asked to review a methodology that is nowhere written down. Fix: one static "Methodology & Limitations" page (AAOIFI version, thresholds, screening source description within Rule 12 limits, staleness rules, purification explanation, "not a fatwa"). Documentation-heavy, zero provider cost.

### Verdict: **Ready after these specific fixes — not ready today.**

The core the Mufti will probe hardest — the gate, the honesty of the states, the refusal to guess — is genuinely built and holds under inspection. What is *not* ready is the wrapping: the first screen contradicts the ethic, the paid tier is fictional, and the methodology he is being asked to review is undocumented. Shortest credible path, in order:

1. Landing honesty + footer disclaimers (C13.1) — small, no cost.
2. Remove/relabel Pro (C13.2) — trivial.
3. Methodology & Purification page (C13.3) — writing work.
4. Fix the Finnhub crash path (item 13) so the demo cannot die mid-meeting — one small approved code change.
5. Update the stale docs (V1–V6) so nothing in the repo contradicts what he is shown.
6. On the day: warm the backend, and pre-screen the 2–3 demo tickers (~10–15 of the 177 tokens, spent deliberately, with your explicit go-ahead — never automatically).

All of these are covered as Phase 0 in the new `WHAT_TO_DO_NEXT.md`.
